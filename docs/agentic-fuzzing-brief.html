CONTEXT

What this actually is

This is not coursework — it is a screening exercise for a PhD position. Prof. D'Amorim invited 39 people out of 563 applicants and asked each to attempt one shared assignment. The work you submit is the main evidence he uses to identify the strongest candidates, so it is judged less on "did it run" and more on the quality of your judgment: how you reason about a hard problem, how you design a feedback loop, and how honestly you report what you found.

The one-sentence goal

Teach a language model to write an ever-better "weird input generator" from a file format's rulebook, use it to crash a C parser, and prove exactly which distinct bugs you found.

CONCEPTS

The moving parts, in plain terms

Fuzzing means automatically generating many strange inputs and feeding them to a program to make it crash. Each genuine crash is a real bug.

A sanitizer (the -fsanitize=address,undefined build flag) is a smoke detector for C: it makes silent memory bugs abort loudly and print a report saying exactly what broke and where, so nothing hides.

The harness is a tiny C wrapper you write — read an input, hand it to the library's parse function, exit. It is the thing you run thousands of times.

Hypothesis is a Python library that generates test data from a recipe you write (called a strategy). Crucially, when an input triggers a crash it automatically shrinks it down to the smallest version that still crashes.

A grammar is a precise rulebook describing what valid input looks like. You copy a ready-made one from the public ANTLR grammars-v4 repository rather than writing your own.

Why involve an LLM at all

Random bytes are useless against a parser — it rejects garbage at the first character and you never reach the deep code where bugs live. You want inputs that are mostly valid but weird: deep nesting, extreme numbers, odd Unicode, valid-until-the-last-character. Writing that generator by hand is tedious — so you have the LLM write it, then improve it round after round.

TARGET

Why parson (JSON)

Of the six offered libraries, parson is the safest strong choice for this specific test:

  • The assignment itself reports that a trial run on parson went from 0 crashes to reliably finding crashes in 5 iterations — so bugs are known to be findable with this exact method. That removes the worst outcome: "found nothing."
  • JSON is recursive (objects inside arrays inside objects), and the assignment requires your generator to use recursive strategies — a skill you literally cannot show off on the flat formats (INI, CSV).
  • JSON has the cleanest grammar in grammars-v4 and the smallest gap between spec and real library behaviour.
  • It is a single small C file — minimal time lost fighting the build.

Backup: json-parser — same grammar and difficulty, a different and less-hardened codebase, so results read as yours rather than a repeat of the demo. A drop-in swap if you want a touch more originality.

METHOD

The six steps

  1. Find the grammar

    Pull the JSON grammar from ANTLR grammars-v4. Document any place the real parson parser accepts more or less than the formal grammar — that gap analysis is itself a graded deliverable.

    OUT → grammar file + notes on real-vs-spec differences

  2. Build the harness

    Write a small C driver (read stdin → call parse → exit) and a build script that compiles library + harness with the sanitizers. Demonstrate it behaves correctly on a few valid and invalid samples before moving on.

    OUT → harness.c + build.sh, verified on samples

  3. Baseline strategy

    Wire the whole pipeline with a deliberately naive generator (random text) just to prove the plumbing: generate → run → detect crash/non-crash → log. Goal is plumbing, not bugs.

    OUT → working end-to-end pipeline

  4. The agentic loop

    The core. Each round: the LLM writes/revises a Hypothesis strategy from the grammar; you sanity-check that its output is mostly accepted (not rejected 99% of the time); run ~500 examples through the harness; summarize crashes, rejection reasons, and structural diversity; feed that back and ask for a better version. Repeat up to 5 times.

    OUT → loop code, final generator, evolution log

  5. Crash triage

    Group crashes by a signature hashed from the sanitizer stack trace (many crashes are often one bug); shrink each unique bug to a tiny reproducer with Hypothesis; re-run each reproducer standalone to confirm it is deterministic.

    OUT → deduplicated, minimized, verified reproducers

  6. Write the report

    A two-page write-up covering design, findings, and challenges — readable by someone who never saw the assignment. Code, logs, and raw crash dumps go in an appendix and do not count against the two pages.

    OUT → 2-page report + artifacts repo

JUDGMENT

The three calls that get graded hardest

1 · Crash vs. rejection vs. valid. Your harness must cleanly separate three outcomes. Mislabelling a polite rejection as a crash floods your triage with false positives.

exit 0 — valid parse clean exit — well-formed rejection signal / sanitizer — real bug

2 · Your proxy signal. Real fuzzers steer by code coverage; this assignment forbids it ("blackbox"). So you must pick a substitute compass — acceptance rate, error-message diversity, structural diversity, crashes found — and justify why it should drive improvement. This design choice is called out as a primary grading criterion.

3 · Timeouts are bugs too. An input that makes the parser hang (cut off after 5 seconds) counts as a crash — a parser you can freeze is a denial-of-service vulnerability, and it goes through the same triage.

The message behind the tight budget: brute force will not save you. If it is not working within 5 iterations, the intended fix is a smarter feedback signal, not more rounds.
